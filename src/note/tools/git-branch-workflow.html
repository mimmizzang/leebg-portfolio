Git branch & workflow

안전한 독립 작업 환경을 구축하고 충돌 없는 협업을 위한 체계적인 브랜치 관리 전략

소개

프로젝트 규모가 커질수록 하나의 브랜치에서 모든 코드를 수정하는 방식은 예기치 못한 충돌과 결함을 초래할 위험이 큽니다. 공들여 만든 메인 코드가 사소한 실수로 망가지는 상황은 개발자에게 큰 심리적 부담이자 프로젝트의 치명적인 지연 요소가 됩니다.

이러한 걱정 없이 오직 기능 구현에만 집중할 수 있도록 작업용 브랜치 방식을 도입했습니다. 완성본인 main은 보호하고 새로운 작업이나 수정 사항은 독립적인 작업 브랜치에서 테스트한 뒤 검증을 거쳐 합치는 안전한 흐름을 설계했습니다.

예제 화면

프로젝트에 사용했던 Git 핵심 흐름도입니다.

예제 코드

git pull

작업 시작 전 원격 main의 최신 소스를 동기화하여 코드의 일관성을 유지하고 발생 가능한 충돌을 사전에 방지했습니다

git checkout -b

기능 단위로 독립된 브랜치를 생성하여 메인 브랜치의 안정성을 유지하고 여러 기능을 동시에 개발할 수 있는 구조를 구축했습니다.

git merge

개발이 완료된 기능을 검증용 dev 브랜치에 통합하여 전체 시스템과의 호환성을 확인하고 안전하게 코드를 병합했습니다

git push

로컬에서 검증을 마친 최종 작업물을 원격 저장소에 반영함으로써 작업 이력을 안전하게 보존하고 배포가 가능한 최신 상태를 유지했습니다. 

# 1. 초기 브랜치 세팅 (최초 1회만 실행)
git checkout main
git pull origin main 
git branch dev		# 로컬 dev 생성
git push origin dev	# 원격에 dev 반영

# 2. 새로운 기능 개발 시작
git checkout dev		# 개발 브랜치로 이동
git pull origin dev		# 최신 상태 업데이트
git checkout -b feat/~~	# 작업용 브랜치 생성 및 이동

# 3. 작업 완료 및 로컬 기록
git add .
git commit -m "feat: ~~"

# 4. 개발 브랜치(dev)에 병합 및 검증
git checkout dev
git pull origin dev		# 병합 전 최신화
git merge feat/~~		# 기능 병합
git push origin dev	    # 원격 dev에 공유
git branch -d feat/~~

# 5. 최종 배포 (main 반영)
git checkout main
git pull origin main 
git merge dev		    # 검증된 dev를 main에 병합
git push origin main	# 최종 배포

비교 분석

1인 개발 환경에서 효율성만 따진다면 단일 브랜치 방식이 빠를 수 있으나 프로젝트의 지속적인 성장과 실무 협업 환경을 목표로 하였기에 전략적 브랜치 워크플로우를 채택했습니다. 기능별 독립 브랜치(feat/)를 운영함으로써 메인 코드의 오염을 차단하고 작업 단위별로 명확한 히스토리를 남겨 미래의 내가 코드를 다시 보더라도 한눈에 파악할 수 있어 과거의 작업 흐름을 이어갈 수 있는 효율적인 관리체계를 갖출 수 있었습니다.

dev 브랜치를 통한 단계별 검증 절차는 단순한 개발 습관을 넘어 실제 서비스 환경(main)에 미치는 영향을 최소화 하는 무중단 배포의 안정성을 확보하기 위한 장치입니다. 이는 당장의 작업량을 늘리는 것처럼 보일 수 있으나 최종 프로덕트에 반영하기 전 통합 테스트를 거치는 습관을 몸에 익혀 잠재적 오류를 사전에 걸러내는 실무적 감각을 기르는 과정이었습니다. 결과적으로 이러한 워크플로우는 개인 프로젝트를 넘어 팀 단위 협업의 기본 원리를 직접 경험하고 익히는 밑거름이 된다고 생각합니다.

주요 학습 포인트

기본적인 Fast-forward 병합을 주로 활용했으나 프로젝트 규모가 커지며 기능별 작업 단위가 모호해지는 한계를 경험했습니다. 이를 해결하기 위해 터미널의 git log --graph 와 GitHub Network 탭을 활용해 히스토리를 시각화하여 확인하는 법을 익혔으며 실무 협업에서 기능 단위의 병합 이력(Merge Commit)을 남기는 --no-ff 전략의 중요성을 이해하게 되었습니다. 또한 공용 브랜치에 기능을 합치기 전 작업 브랜치 내에서 상위 브랜치의 최신 변경 사항을 먼저 통합해 보는 선제적 병합(Pre-merge) 프로세스를 익혀 잠재적인 오류를 로컬 환경에서 미리 검증하고 해결하는 안정적인 개발 습관을 체득했습니다.

직전 커밋의 사소한 실수를 수정하는 git commit --amend와 특정 시점으로 되돌리는 reset의 차이를 명확히 인지하고 상황에 맞춰 활용했습니다. 이미 원격 저장소에 공유된 기록을 다룰 때는 투명성을 위해 revert를 사용하는 협업 매너를 학습했습니다. 특히 강제 푸시(--force)의 위험성을 인지하고 혼자 작업할 때의 효율적인 이력 정돈과 팀 단위 협업 시의 안정성을 모두 고려한 명확한 대응 기준을 세웠습니다. 이러한 경험은 단순히 도구를 사용하는 수준을 넘어 실무 환경의 리스크를 관리하며 안정적인 프로덕트 운영 역량을 체득하는 소중한 과정이 되었습니다.
